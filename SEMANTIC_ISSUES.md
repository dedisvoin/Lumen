# Семантические недочёты и неоднородности языка Lumen

> Результат эмпирического анализа: прогон пробников в режимах `-r`
> (интерпретатор) и `-build` (транспиляция), сверка с `LANG.md`,
> `keywords/*.md`, `all_semantic.lm` и исходниками
> (`compiler/CodeGenerator.cpp`, `compiler/DeepAnalizer.cpp`,
> `compiler/runtime/lumen_rt.h`, `compiler/core/TypeSystem.cpp`).
>
> Большинство выводов одинаковы в обоих режимах — это дефекты языка,
> а не расхождения рантайма. Ниже для каждого пункта — минимальный пример.

---

## A. Критические семантические дефекты

### A1. `&&`, `||`, `??` НЕ короткозамкнутые — правый операнд вычисляется всегда

> **СТАТУС: ИСПРАВЛЕНО.** Правый операнд теперь вычисляется лениво
> (короткое замыкание) и в интерпретаторе, и в транспиляции.
> Правка: `lumen_rt.h` (`land`/`lor`/`coalesce` принимают thunk),
> `CodeGenerator.cpp:652-663` (эмитит `[&]() -> rt::Box {...}`),
> `DeepAnalizer.cpp` (`NodeBinaryLogicalAnd`/`LogicalOr`/`NullCoalesce`).
> Проверено: `p07b_shortcircuit.lm`, `p07c_coalesce.lm` в `-r` и `-build`;
> регрессия 65/0 (набор `~ FAIL` интерпретатора идентичен baseline).

```lumen
fn side() -> bool : { echo "called"; ret true; }
echo false && side();   // (было) печатает "called", потом false  ← НЕВЕРНО
echo true  || side();   // (было) печатает "called", потом true   ← НЕВЕРНО

let x = null;
echo x ?? side_val();   // (было) правый операнд тоже вычисляется
```

Побочный эффект — ложные ошибки вычисления:
```lumen
let x = 0;
echo x != 0 && 20 / x > 0;   // (было) error[70] Division by zero (правая часть вычислена)
```

Причина: `CodeGenerator.cpp:653-657` эмитил `rt::land(l, r)` / `rt::lor(l, r)`,
а `lumen_rt.h:707-720` принимал оба аргумента уже вычисленными
(комментарий прямо признавал: «оба операнда вычислены заранее»;
то же для `coalesce`, `:716`). При этом `keywords/and.md:14` обещал
короткое замыкание — документация противоречила поведению.

### A2. Операторы `<`/`>` для строк сравнивают ДЛИНУ (в байтах), а не содержимое

> **СТАТУС: ИСПРАВЛЕНО (вариант «запретить»).** Порядковые операторы
> `<` / `>` / `<=` / `>=` для строк **удалены**: теперь это ошибка
> `error[81] BINARY_COMPARE_INVALID_TYPE`. Для строк оставлены только
> `==` и `!=` (сравнение содержимого). Правка: `lumen_rt.h` (`cmp` — убрана
> ветка `T_STR` для порядка), `DeepAnalizer.cpp` (убраны ветки `Ty::Str`
> в `NodeBinaryLess/Greater/LessEqual/GreaterEqual`),
> `ErrorBase.cpp` (обновлён hint). Документация `keywords/str.md` приведена
> в соответствие. Регрессия 65/0.

Было (сравнение по UTF-8-длине, не по содержимому):
```lumen
echo "a" < "b";          // было false  ← должно было быть true
echo "abc" < "abd";      // было false
echo "apple" < "banana"; // было true   (просто потому что 5 < 6)
echo "я" < "zz";         // было false  (2 байта vs 2 байта)
```

Стало:
```lumen
echo "apple" == "banana"; // false   (== / != работают)
echo "apple" != "banana"; // true
echo "apple" < "banana";  // error[81] Values of type 'str' cannot be compared with '<'
```

Причина (было): `lumen_rt.h:698-702`:
```cpp
} else if (l.t == Box::T_STR && r.t == Box::T_STR) {
    size_t a = l.s.size(), b = r.s.size();   // <-- сравнивалась длина в БАЙТАХ
    if (op == '<' || op == 'L') res = a < b;
    else if (op == '>' || op == 'G') res = a > b;
    ...
}
```

### A3. Равенство `==` НЕ приводит числовые типы, а сравнение порядка — приводит

> **СТАТУС: ИСПРАВЛЕНО.** `==`/`!=` теперь выполняют числовое приведение,
> как и порядковые операторы. Правка: `lumen_rt.h` (`cmp` — числовая ветка
> через `num()` перед проверкой `l.t == r.t`), `DeepAnalizer.cpp`
> (`NodeBinaryEqual`/`NodeBinaryNotEqual`). Регрессия 65/0.

Было:
```lumen
echo 1 == 1.0;   // было false   ← удивляет
echo 1 != 1.0;   // было true
echo 1 < 1.5;    // true    ← а тут приведение работало
echo 1 <= 1.0;   // true
```

Стало (согласовано с порядком):
```lumen
echo 1 == 1.0;   // true
echo 1 != 1.0;   // false
echo 1 < 1.5;    // true
echo 1 <= 1.0;   // true
```

Причина (было): `cmp` (`lumen_rt.h:668-689`) требовал `l.t == r.t` для
`==`/`!=`, но в ветке порядка (`:693`) использовал `is_num(l) && is_num(r)`.
Теперь обе ветки используют числовое приведение для чисел (число-число),
а прочие типы сравниваются как раньше (по совпадению типа).

### A4. `char` поддерживает `==`, но НЕ `<`; при этом enum сравнивается

> **СТАТУС: НЕ БАГ — так задумано.** Порядок для `char` сознательно запрещён
> (проверка кода символа не является осмысленным сравнением); порядок для
> `enum` — намеренно разрешён (порядок элементов объявления). Изменений не
> требуется.

```lumen
echo 'a' == 'a';   // true   (равенство кода символа — ок)
echo 'a' < 'b';    // error[81]: Values of type 'char' cannot be compared with '<' against type 'char'

enum C { A, B }
echo C::A < C::B;  // true   ← порядок объявления (намеренно)
```

### A5. Разнобой в «истинности» (truthiness)

> **СТАТУС: ЧАСТИЧНО ИСПРАВЛЕНО (только `1 as bool`).** Числовое приведение к
> `bool` теперь разрешено (ненулевое → `true`), как и обещает хинт. Всё
> остальное в этом пункте — **по задумке** (не баг).
> Правка: `DeepAnalizer.cpp` (`NodeCast` — ветка `numeric → bool`); рантайм
> (`rt::cast`, «bool») уже поддерживал. Регрессия 65/0.

```lumen
if (1) { "t" } else { "f" };   // "t"  (число допустимо) — задумано
echo !5;                        // false — задумано
echo 1 as bool;                 // true   ← ИСПРАВЛЕНО (было error[165])
echo 0 as bool;                 // false
echo !'x';                      // error[159] (! нельзя к char) — задумано
echo !"";                       // error[159] (! нельзя к str) — задумано
if ("x") { }                    // error[168] (условие-str запрещено) — задумано
```

Хинт для `as` («supports numeric conversions, bool conversion…») теперь
согласован: `i64 → bool` разрешён.

### A6. Целочисленные литералы всегда `i64`; `i8/i16/i32` почти неприменимы без явного каста

> **СТАТУС: НЕ БАГ — так задумано.** Целочисленные литералы намеренно имеют тип
> `i64`; для строгой ячейки узкого типа нужен явный `as`. Изменений не требуется.

```lumen
strict let a: i8 = 127;        // error[76]: expected 'i8', found 'i64' — задумано
strict let a: i8 = 127 as i8;  // ok
echo 300 as i8;                // 44 (обёртка mod 256)
```

### A7. Печать указателя: шестнадцатеричный префикс к ДЕСЯТИЧНОМУ числу

> **СТАТУС: ИСПРАВЛЕНО.** Адрес печатается в hex (нижний регистр): `0x` + hex.
> Хелперы `formatAddr` (`compiler/DeepAnalizer.cpp`, интерпретатор) и
> `hex_addr` (`compiler/runtime/lumen_rt.h`, рантайм).

```lumen
let p = ptr(0x1000, i64);
echo p;   // 0x1000   (было 0x4096 — "0x" + decimal)
```

Примечание: формат вывода согласован, но **значения** адресов `new`/`&x`
по-прежнему различаются между режимами (`-r` — высокобазовая арена
`0x1000…`, `-build` — низкие индексы/`ptr`). Это отдельная схема адресации,
не формат печати.

## B. Документация противоречит реализации

### B1. Литерал массива

> **СТАТУС: ИСПРАВЛЕНО.** `keywords/Array.md` переписан: дженерик в квадратных
> скобках `Array[i64]`, литерал `{...}`. Было две ошибки в примере из доков.

`keywords/Array.md` показывал `let arr: Array<i32> = [1, 2, 3];`. Фактически:
- дженерик — в **квадратных** скобках: `Array[i32]` (а не `<i32>`, → `error[38]`);
- литерал массива — `{...}` (а не `[...]`, → `error[49]`);
- целочисленные литералы всегда `i64` (A6), поэтому `Array[i32]` требует кастов.
```lumen
let a: Array[i64] = {1, 2, 3};                 // ok
let b: Array[i32] = {1 as i32, 2 as i32};      // ok (литералы — i64)
let c: Array[i32] = {1, 2, 3};                 // error[83]: expected '{i32, ...}', found '{i64, 3}'
```

### B2. `del` для освобождения памяти

> **СТАТУС: НЕ БАГ — так задумано** (по решению пользователя, пока не трогаем).
> Перегрузка `del` (элемент массива vs освобождение указателя) сохранена как есть;
> поведение подтверждено. Изменений в этой итерации не требуется.

`keywords/del.md` — `let p = new 0; del p;`. Фактически:
```lumen
let p = new 5;
del p;        // error[124]: 'del' requires an index for type '*(i64)'
del a, 1;     // а это удаляет ЭЛЕМЕНТ массива — другое значение
```
`del` перегружен (элемент массива vs освобождение указателя), но
документирован только один смысл.

### B3. Печать структуры

> **СТАТУС: НЕ БАГ — так задумано** (по решению пользователя, пока не трогаем).
> Печать структуры как `object(P)` — намеренное поведение; комментарии в
> `all_semantic.lm` (`// {value: 5}`) устарели и в этой итерации не трогаются.

`all_semantic.lm:446` — `outln cnt; // {value: 5}`; `:450` —
`outln cnts; // {{value: 1}, {value: 2}}`. Фактически в обоих режимах:
```lumen
struct P { strict let x: i64; strict let y: i64; }
let p = P { x: 1, y: 2 };
echo p;    // object(P)
outln p;   // object(P)
```

### B4. `and`/`or`/`is`/`in`/`do`

> **СТАТУС: ОТЛОЖЕНО.** Поддержку этих ключевых слов пользователь добавит позже;
> сейчас оставляем как есть. Не трогаем в этой итерации.

Есть `keywords/and.md`, `or.md`, `is.md`, `in.md`, `do.md`, но:
```lumen
echo true and false;  // error[38] (только && / || / !)
echo 5 is i64;        // error[38]
echo 5 in {1, 2, 3};  // error[38]
do { } while (0);     // error[149]
```

### B5. `append` — оператор, а не функция

> **СТАТУС: НЕ БАГ — так задумано.** `append` — оператор (`append a, 4;`),
> вызов в виде функции не предусмотрен. Оставляем как есть.

`append.md` описывает `append a, 4;`. Вызов `append(a, 4)` падает:
```lumen
append a, 4;    // ok
append(a, 4);   // error[38]
```

### B6. `?T` в типах

> **СТАТУС: ИСПРАВЛЕНО (документация).** Добавлены разделы про составные типы
> (union `A | B` и nullable `?T` = `T | Null`) в `keywords/Type.md` и
> `keywords/Null_type.md`.

`?i64` в `typeis` отображается как `i64 | Null` — то есть `?` есть
синтаксический сахар над union, а не отдельная сущность.
```lumen
let a: ?i64 = null;
echo typeis(a);                   // i64 | Null
echo typeis(a) == (i64 | Null);   // true
```

Ошибка в исходной доках: префиксный `!T` **не** создаёт nullable — только `?T`
(`!i64` → `error[159]` «Operator '!' cannot be applied to type 'Type'»).
`!T` убран из документации: LANG.md (строки 24, 156, 198, 399-400, 1270, 1281),
`keywords/Null_type.md` и `compiler/plan/transpilation-all-semantic.md`
(строки 11, 32, 82, 316, 319, 528). Префиксный `?` на Type-значении (§8.6) оставлен.

## C. Неоднородности типовой системы

### C1. Тип массива зависит от длины

```lumen
echo typeof({1, 2});                        // {i64, 2}
echo typeof({1, 2, 3});                     // {i64, 3}
echo typeof({1, 2}) == typeof({1, 2, 3});   // false
echo typeof({1, 2}) == Array[i64];          // false
echo Array[i64];                            // {i64, ...}
```
`Array[i64]` (без длины) не равен типу конкретного массива — сомнительно
для системы типов.

### C2. Массивы в рантайме разнородны, хотя задокументированы как однородные

```lumen
let m = {1, "two", 3.0, true};   // ok, {1, two, 3, true}
```
Однородность обеспечивает только `strict Array[T]`.

### C3. Иерархия сравнимости непоследовательна

Сравнимы: числа, bool, char (только `==`), str, null, Type, enum (порядок).
НЕ сравнимы: массив, кортеж, структура (без `__eq__`).
```lumen
echo {1, 2} == {1, 2};    // error[81] массив не поддерживает равенство
echo !{1, 2} == !{1, 2};  // кортеж — то же
```

### C4. Разное представление кортежа и массива

```lumen
echo {1, 2, 3};       // {1, 2, 3}      — фигурные
echo !{1, 'a', true}; // [1, a, true]   — квадратные
```

### C5. `char + int` запрещён, но `char * int` (повтор строки) разрешён

```lumen
echo 'a' + 1;    // error[181] implicit arithmetic on 'char'
echo 'a' * 3;    // "aaa"
echo 'a' + "bc"; // "abc"
echo "ab" + 'c'; // "abc"
```

### C6. `str + число` запрещено, хотя вывод почти всегда нужен

```lumen
echo "n: " + 5;  // error[72]: Unsupported operator '+' for str and i64
```

### C7. `del`/индексация: нет отрицательных индексов и срезов

```lumen
echo a[-1];    // error[158] Array index -1 ...
echo s[0..2];  // error[37]/[38] нет срезов
del s, 1;      // error[123] 'del' expects Array or Tuple, found 'str'
```

### C8. Тип как значение vs тип, зависящий от рантайма

`typeof(1)` = `i64`, но `typeof({1,2})` включает длину (см. C1).
`typeis(x)` даёт объявленный тип (`i64 | f64`), `typeof` — текущий (`i64`).

## D. Функции, замыкания, вызовы

### D1. Лямбды в рантайме == `Null`

```lumen
let d = lambda(v: i64) -> i64 : { v * 2 };
echo d(21);   // error[95]: Call attempted on value of type 'Null'
```
Задокументировано как «не работает» (`all_semantic.lm:118`), но остаётся
дырой.

### D2. `Func` как тип без параметров не парсится

```lumen
fn g(f: Func) -> i64 : { ret 0; }        // error[38]: Expected '['
fn g(f: Func[i64]) -> i64 : { ret 0; }   // (требуется форма с '[...]')
```

### D3. Именованные аргументы не поддерживаются, дефолтные — да

```lumen
fn f(a: i64, b: i64 = 10) -> i64 : { ret a + b; }
echo f(1);            // 11 (дефолт работает)
echo f(b = 2, a = 1); // error[38]
```

### D4. `ret` запрещён в лямбде

Тело лямбды — выражение, `ret` вне функции → `error[42]`.

## E. Синтаксические неоднородности

### E1. `for` требует `;` после update

```lumen
for (let i = 0; i < 3; i = i + 1;) { ... }  // ok — с «лишним» ';'
for (let i = 0; i < 3; i = i + 1)  { ... }  // error[38]
```

### E2. Нет тернарного `?:`, нет `**`, нет цепочек сравнения

```lumen
echo n > 3 ? "big" : "small";  // error[38]
echo 2 ** 3;                   // трактуется как двойной * (deref) → error
echo 1 < 2 < 3;                // error[81] (bool < i64)
```

### E3. `out`/`outln` молчат в интерпретаторе, но печатают в скомпилированной программе

В `-r` видимый вывод даёт только `echo`; `out`/`outln` — только
`-c`/`-build`. Асимметрия режимов (см. `LANG.md`).

### E4. `++`/`--` работают как постфикс, но не отражены в списке ключевых слов

Нет `inc.md`/`dec.md`; неизвестно, есть ли префиксная форма:
```lumen
let i = 0;
i++;      // работает, i == 1
```

## F. Ошибки / диагностика

### F1. Нумерация кодов неупорядочена семантически

`final` → `error[82]`, `const` → `error[91]` (константа «позже» final,
хотя должна быть мягче); `private` → `error[102]`.

### F2. Каскадные ошибки

Одна ошибка синтаксиса/типа часто «убивает» переменную и порождает
лавину `error[73] Undefined variable` (см. `strict let a: i8 = 127;`),
зашумляя вывод.

### F3. Неточные сообщения

Для строк `error[158]` говорит «Array index … (size 5)» — это строка,
а не массив.

## G. Что, наоборот, согласовано (проверено)

- `ref`-алиасы, `ref`-параметры, `&`/`*`, `new`, `ptr` — работают.
- `strict` / `const` / `final` — реально блокируют (`error[83]/[91]/[82]`).
- `private` (namespace/struct) — блокирует доступ (`error[102]`).
- `mod(x, strict|final|public)` — работает.
- `typeof` / `typeis` — соответствуют докам.
- Dunder `__add__` / `__eq__` / `__sizeof__` / `__assign__` — работают.
- `?T` и `??` — работают (но `??` не короткозамкнут, A1).
- Интерпретатор и компилятор совпадают на протестированных кейсах
  (числа, строки, структуры, массивы).
